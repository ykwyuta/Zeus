# 0012: COBOL の C1 網羅テストケースの自動生成

与えられた COBOL プログラムについて、すべての分岐 (判定) の両方向を通るテストケース (C1、判定網羅) を自動で作る。
入力は**動的記号実行 (concolic 実行) と SMT ソルバ**で求める。生成 AI に入力を決めさせることはしない (ヒントとして
入力の候補を出させる使い方は「効率化と生成 AI のヒント」で検討する。その場合も、網羅と期待値は実行の結果で決める)。
生成したテストは Zeus の通常のインタプリタで実行し、0010 のカバレッジ (`zcov`) で網羅率を確かめる。

この文書は方式の提案で、実装は段階的に行う (「段階計画」)。実装済みの範囲は末尾の「実装 (2026-10)」に、検証からわかった向き・不向きは「向いているもの・向いていないもの」に、今後の改善の順序は「改善の進め方」に記す。

## 目標と成果物

- 入力: COBOL のソース (または `.zo`)、COPY ライブラリー、必要なら呼び出すサブプログラム。
- 出力:
  1. **テストケース**: 入力 (LINKAGE・ファイルのレコード・ACCEPT・CICS / SQL の応答など) と、その入力での出力
     (DISPLAY、書いたレコード、LINKAGE の最終値、RETURN-CODE、発行した CICS / SQL 要求)。Zeus でそのまま再実行
     できる形式 (後述の `ztest`)。
  2. **網羅の報告**: 分岐ごとに、通したテストケース、または通せなかった理由 (到達不能の証明、時間切れ、
     未対応の文、環境のモデル不足)。
  3. 生成したテストを通常のインタプリタで実行した `zcov` の結果 (生成器の自己申告ではなく実測で C1 を示す)。
- 期待値は「現在の振る舞い」を記録したもの (特性テスト、回帰テスト用)。仕様として正しいかは人が確認する。
  ただし実行時の異常 (データ例外 S0C7 相当、添字範囲外、0 除算、無限ループの打切り) は見つけた不具合として報告する。

### C1 の定義

C1 は ZIR の条件付き飛越しの両方向とする。0010 のカバレッジが数える分岐と同じで、`zcov` でそのまま測れる。

- IF、EVALUATE の WHEN (と OTHER)、PERFORM UNTIL / VARYING の判定、SEARCH / SEARCH ALL、GO TO DEPENDING ON、
  AT END / NOT AT END、INVALID KEY、ON SIZE ERROR、ON OVERFLOW、ON EXCEPTION、USE 手続きへの分岐。
- 複合条件 (`A AND (B OR C)`) は Zeus のコード生成で 1 つの `Cx` になり、1 回の `JumpIf` で判定される (短絡評価の
  飛越しに分かれない)。したがって ZIR の分岐 = ソースの判定で、C1 (判定網羅) に一致する。条件網羅 (C2) や
  MC/DC は拡張として後で扱える (`Cx` の葉ごとに目標を立てる)。

## 方式の比較

| 方式 | 長所 | 短所 | 判断 |
|---|---|---|---|
| ランダム・ファジング | 実装が簡単、速い | `IF WS-USER = 'ADMIN001'` や 88 レベルの特定値、桁の境界を偶然には当てられない | 種 (seed) と補助に使う |
| 探索ベース (分岐距離 + 遺伝的アルゴリズム) | ソルバ不要、数値の大小には強い | 文字列の一致、REDEFINES をまたぐ条件、複数変数の関係に弱い | ソルバが解けないときの代替 |
| 静的記号実行 (全経路の列挙) | 実行しない部分も推論できる | COBOL の実行時意味 (10 進演算、MOVE の変換、INSPECT など) を全部モデル化する必要、経路爆発 | 採らない |
| **動的記号実行 (concolic)** | 具体値で実際に実行しながら記号の制約を集めるので、モデル化できない操作は具体値に固定して先へ進める。既存インタプリタの意味をそのまま使える | ソルバの性能、環境 (ファイル・CICS・SQL) のモデルが要る | **採用** |

concolic 実行 (DART・CUTE・KLEE・SAGE の系統) を中心に、ファジングで初期入力を作り、ソルバが解けない分岐は
分岐距離による探索で補う。

## 全体の流れ

```text
          +-------------------+    経路条件         +---------+
 入力 --> | 記号付き実行      | ----------------->  | 探索器  | -- 未到達の分岐を選ぶ
 (具体値) | (ZIR インタプリタ |                     |         |    経路の接頭辞 + 否定した条件
          |  + 影の記号メモリ)| <-- 新しい入力 ---- | ソルバ  | <--
          +-------------------+                     +---------+
                  |
                  v
         テストケース (入力・出力)  -->  最小化  -->  ztest で再実行・zcov で計測
```

1. 初期入力 (空白とゼロ、またはファジングの入力) でプログラムを実行する。
2. 実行中、入力に由来する値を **記号式** として影のメモリに持ち、分岐ごとに「どちらに進んだか」と
   その条件式を経路条件として記録する。
3. 探索器が、まだ片方しか通っていない分岐を選び、そこまでの経路条件 + その分岐の否定をソルバに渡す。
4. 充足可能なら解 (モデル) を新しい入力にして 1 へ。充足不能なら、その経路ではその向きに進めないと記録する。
   すべての経路で充足不能 (到達し得る経路条件の和が矛盾) なら到達不能として証明付きで報告する。
5. 打切り (時間・実行回数) まで繰り返し、網羅に寄与したテストケースを残す。

## 記号付き実行 (Zeus への組み込み)

- **実行は既存のインタプリタ**: `Machine::exec_step` (ネイティブコード化で導入した 1 命令ずつの実行) を使い、
  各命令の前後で記号の層を動かす。具体値の計算は常にインタプリタが行い、記号の層は「この値は入力のどの式か」
  だけを追う。これにより生成器と実行系で意味がずれない。
- **影の記号メモリ**: 記憶域 (WORKING-STORAGE、LINKAGE、ファイルのレコード域) のバイト範囲から記号式への写像。
  入力でない範囲は具体値として扱い記号を持たない (大半の命令は記号の処理をせず素通りする)。
- **命令ごとの記号の意味** (ZIR の `Instr`・`Ex`・`Cx` に対応):

| ZIR | 記号の扱い |
|---|---|
| `Move(Src, Loc)` | 型の変換を式で表す: 数値→数値 (桁合わせ・切捨て = 定数での除算と剰余)、英数字→英数字 (切詰め・空白詰め)、数値→英数字・編集項目 (初期は具体値に固定) |
| `Store`・`DivRem`・`Ex::Bin` | 整数 (スケール付き) の演算。ROUNDED、桁あふれ (`SizeError` の分岐) は 10^n との比較で表す |
| `JumpIf`・`JumpUnless`(`Cx`) | 分岐の記録点。`Cmp` (数値・英数字・照合順序)、`Class` (NUMERIC など)、`Sign`、`And`・`Or`・`Not`、条件名 (88) はコード生成済みの比較 |
| `GoDepending`・`SearchStep` | 多方向の分岐。各行き先を目標にする |
| `Read`・`Write`・`Call`・`Exec` | 環境のモデル (後述)。結果の状態 (`IoCond`・`CallException`、SQLCODE、RESP) を記号の選択肢にする |
| `Inspect`・`StringStmt`・`Unstring`・関数 | 初期は具体値に固定 (結果を具体化し、入力への制約として「この値だった」を加える)。後で文字列理論や専用の符号化を追加 |
| 記号の添字・参照修飾 (OCCURS、`(i:n)`) | 範囲外を目標にする分岐を加えたうえで、配列理論で表すか、具体値に固定する |

- **具体化 (concretization)**: 記号の層が扱えない命令では、その時点の具体値で式を固定し、経路条件に
  「式 = 具体値」を加える。網羅のための入力生成としては健全 (解は必ずその経路を通る) で、扱える範囲を広げるたびに
  網羅が上がる設計にできる。

## データの記号表現

COBOL の記憶域はバイト列で、REDEFINES や MOVE で同じバイトを別の型として読むため、表現は 2 層にする。

1. **バイト層 (正)**: 入力の各バイトをソルバの 8 ビット変数とする。英数字・グループ・REDEFINES はこの層で扱う。
2. **値の層 (速さのため)**: 数値項目は、書き込まれた型のまま整数の式 (スケール付き) として持つ。読む型が一致すれば
   変換せずに使い、異なればバイト層へ下ろす (ゾーン 10 進は各桁 `F0`〜`F9` と符号の半バイト、パック 10 進は
   半バイトの桁と符号、2 進はビッグエンディアンのビット列)。
   - 入力の数値項目は、既定では **正しいデータ** を仮定して整数変数 1 つで表す (PIC S9(5)V99 なら
     -9999999 ≦ x ≦ 9999999、値は x / 100)。式が小さく、ソルバが速い。
   - `IF X NUMERIC` のような分岐があるときだけ、その項目をバイト層の変数に切り替え、不正なデータも作れるようにする。
- **英数字の比較**: 長さの違いは空白で埋め、照合順序は EBCDIC のバイト順 (PROGRAM COLLATING SEQUENCE があれば
  その変換表を配列として与える)。固定長なので、ビットベクトルの比較の連鎖で表せる。
- **10 進演算**: Zeus の `Dec` と同じく、整数とスケールで正確に表す。加減算は線形、定数との乗除算も線形
  (整数除算と剰余)。変数どうしの乗除算は非線形になるので、ソルバが答えないときは片方を具体値に固定する。
- COMP-1 / COMP-2 (浮動小数点) は、初期は具体値に固定する (後で浮動小数点理論)。

## ソルバ

- **Z3** (MIT ライセンス) を第一候補にする: 整数・ビットベクトル・配列・(将来) 文字列の理論、増分求解
  (push / pop)、充足不能の核 (unsat core)。Rust からは `z3` クレート (libz3 をリンク) で使い、`zeus-testgen` の
  feature にする。ソルバは trait の裏に置き、cvc5・Bitwuzla と差し替えられるようにする。
- **自前の高速経路**: 1 変数の範囲制約 (`X > 100 AND X <= 200`)、等号 (`WS-CODE = 'A1'`)、少数の
  選択肢 (88 レベル) は区間と集合の計算で直接解き、ソルバを呼ばない。COBOL の分岐の多くはこの形で、速さに効く。
- **モデルの選び方**: 「関係しないバイトは空白、数値はゼロ」を優先する (Z3 の最適化や、既定値への仮割当ての
  後での補正)。読みやすいテストデータにするため。
- **キャッシュ**: 制約集合 → 結果をキャッシュし、部分集合・上位集合の判定で呼び出しを減らす (KLEE の方式)。

## 探索戦略

- 目標は **片方しか通っていない分岐の、通っていない向き**。分岐の識別は `zcov` と同じ (プログラム・命令位置)。
- 目標の選び方: 制御フローグラフで未到達の分岐に近い経路を優先する (距離のヒューリスティック)。目標ごとに、
  その分岐の手前まで同じ経路を通った実行の中から、経路条件が短いものを使う (世代探索、SAGE の方式)。
- **ループ**: PERFORM UNTIL / VARYING は判定の両方向 (繰り返す・抜ける) を通せば C1 を満たすので、展開回数に
  上限を置く (既定 3 回)。OCCURS の表を回すループで、全件を見る必要があるときだけ上限を上げる。
- **段落の要約**: 何度も通る段落 (日付検査、編集) は入口の値 → 出口の値と分岐の要約を作り、再利用する
  (関数要約)。後の段階の最適化。
- **到達不能**: どの経路からも充足不能な分岐は、到達不能 (死んだコード) として、その理由 (unsat core に含まれる
  条件) とともに報告する。網羅率の分母から除くかどうかは利用者が選ぶ。

## 環境のモデル

concolic 実行で一番難しいのは、プログラムの外 (ファイル、CICS、Db2、サブプログラム) との境界である。
外部の結果を **記号の入力** として扱い、生成したテストケースにはその応答 (スタブの値) を含めて再現できるようにする。

| 境界 | モデル |
|---|---|
| PARM・CALL USING の引数 (LINKAGE) | 記号の入力。長さ (PARM の長さ、ODO の件数) も記号 |
| ACCEPT (SYSIN・日付・時刻) | 記号の入力。日付は妥当な日付の制約付き (または固定値を選べる) |
| 順次ファイルの READ | 呼ぶたびに新しい記号のレコード。レコード数 (AT END になる回) も記号で、上限 K 件。FILE STATUS も値の選択肢 |
| 索引ファイル (KSDS) の READ・START | キーの一致・不一致 (INVALID KEY) を記号の真偽で表し、一致したときのレコードを記号にする。同じキーへの再読込の一貫性は制約で保つ |
| WRITE・REWRITE | 出力として記録 (期待値)。状態 (重複キーなど) は記号の選択肢 |
| CALL (ソースがある) | 呼び出し先も記号付きで実行する (プログラムをまたいだ網羅) |
| CALL (ソースがない・提供資産) | スタブ: BY REFERENCE の引数と RETURN-CODE を記号の出力にする。LE サービスなど Zeus が提供するものは実物を使う |
| EXEC CICS | RESP / RESP2 (と HANDLE CONDITION の行き先) を記号の選択肢に、RECEIVE MAP の入力欄・EIBAID・COMMAREA・EIBCALEN を記号の入力に、READ / READNEXT のレコードを記号に。SEND の内容と発行したコマンドは出力 |
| EXEC SQL | SQLCODE を選択肢 (0、+100、-803、-811、-911 など、文の種類ごと) に、SELECT INTO・FETCH の受け取り変数を列の型 (DCLGEN) に従う記号に。発行した SQL とホスト変数の値は出力。実際の Db2 は使わない |
| EXEC DLI・CBLTDLI | 状態コード (空白・GE・GB など) を選択肢に、セグメントを記号に |

スタブの選択肢は、実際に起こり得る値に限る (例: READ の FILE STATUS は 00・10・23・35 など、文と編成から決まるもの)。
「起こり得ない応答」で分岐を通しても意味がないため、選択肢の表をマスタとして持ち、利用者が絞れるようにする。

## テストケースの形式と再実行 (`ztest`)

テストケースは 1 件 1 ファイル (JSON) で、Zeus の実行時にスタブとして差し込む。

```json
{
  "program": "CBACT01C",
  "linkage": { "PARM": "2026-10-01" },
  "files": { "ACCTFILE": { "records": ["<レコード (EBCDIC を 16 進、または項目ごとの値)>"], "status": ["00", "10"] } },
  "accept": [],
  "sql": [],
  "cics": [],
  "expect": {
    "return_code": 0,
    "display": ["..."],
    "files": { "OUTFILE": ["..."] },
    "linkage": { "...": "..." }
  },
  "covers": ["CBACT01C:120:T", "CBACT01C:120:F", "..."]
}
```

- 入力の値は **項目単位** (COPY メンバーの項目名で) でも書けるようにし、人がテストを読める・直せるようにする。
- `ztest run DIR` が全テストを実行し、期待値との差を報告する。`ZEUS_COVERAGE` と組み合わせて `zcov` で C1 を確認する。
- バッチは zjob の DD (ファイル) をスタブのデータで割り当てて実行でき、CICS・SQL はスタブの層 (zcics・zeus-db2 の
  呼出し口にテスト用の応答表) を通す。

## 最小化と読みやすさ

- **集合被覆**: 網羅に寄与しないテストケースを除き、全分岐を覆う最小に近い集合を貪欲法で選ぶ。
- **値の簡約**: 解を得たあと、各入力項目を既定値 (空白・ゼロ) に戻しても同じ分岐を通るなら戻す (デルタデバッグ)。
- **境界値**: 比較 `X > 100` は解が 101 になりやすい。境界を明示的に作る選択肢 (100 と 101 の両方) を設け、
  境界値分析としても使えるようにする。

## 新しいクレートと命令

- `crates/zeus-testgen`: `ztestgen` (生成) と `ztest` (再実行)。zeus-cobol の VM に記号の層の差込み口
  (命令の実行前後のフック、分岐の記録、環境の呼出し口) を加える。通常の実行には影響しない (フックなしは今と同じ)。
- 使い方 (案):

```text
ztestgen [-I DIR]... [--with MODULE]... [--time 600] [--loop-bound 3] [--out DIR] PROGRAM.cbl
ztest run [--coverage DIR] DIR
```

## 制限と危険

- **経路爆発**: 長いバッチ処理や大きな EVALUATE の連鎖では、時間内に全分岐へ届かないことがある。ループの上限、
  要約、目標の優先度で抑え、届かなかった分岐は理由付きで報告する (黙って落とさない)。
- **非線形演算・浮動小数点**: ソルバが答えないときは具体化する。網羅が下がる可能性がある。
- **環境のモデルの妥当性**: スタブの応答は「起こり得る」値の表に依存する。表が粗いと、実環境では起きない
  入力のテストができる。表はマスタとして利用者が確認できるようにする。
- **期待値は現状の記録**: 生成したテストは現在の振る舞いを固定するもので、正しさの判定ではない。
- **意味のずれ**: 記号の層の意味がインタプリタと違うと、解が想定の分岐を通らない。生成した入力は必ず通常の
  インタプリタで再実行し、実際に通った分岐で網羅を数える (記号の層の誤りは「解が効かなかった」として検出し、
  具体化に切り替える)。
- **ライセンス**: Z3 は MIT。IBM のコードは使わない (クリーンルーム規則のまま)。

## 実装 (2026-10)

段階 A、段階 B のうち順次ファイル・索引ファイルの入力と入出力エラーの注入、段階 C のうち CALL のスタブと
呼び出し先のファイル、段階 D の EXEC CICS・EXEC SQL のスタブを `crates/zeus-testgen` (`ztestgen`、`ztest`、
EXEC 文は `stubhost.rs`) と zeus-cobol の記号の層 (`concolic.rs`、
`vm/sym.rs`、ファイル入出力は `vm/sym_io.rs`、試験環境は `vm/testenv.rs`) に実装した。ソルバは外部に依存しない自前のもの (下記) で、Z3 はまだ
組み込んでいない (`Solver` トレイトで差し替えられる形にしてある)。

```text
ztestgen [-I DIR]... [-L DIR]... [--program NAME] [--runs N] [--time S] [--limit N]
         [--no-smt] [--threads N] [--stub PROGRAM]... [--seeds DIR]... [--out DIR] SOURCE.cbl
ztest [-I DIR]... [-L DIR]... [--coverage DIR] SOURCE.cbl CASES-DIR
```

`ztestgen` は `--out` (既定 `tests`) に `case-001.json`… と `report.txt` (網羅率と、通せなかった分岐ごとの理由)
を書く。`ztest` はケースを通常のインタプリタで実行して期待値と比べ、違いがあれば終了コード 1。`--coverage` で
`zcov` の記録を取れるので、生成器の自己申告ではなく実測の C1 を確かめられる。

### 記号の層

- `Machine::exec_step` は記号の状態があるときだけ `sym_step` を通る。ないときの実行は従来と同じ。
- 数値は「桁の整数」の項 (位取り `s` の値は `項 / 10^s`)、英数字はバイトごとの項。シャドウにはバインド時の
  バイトを持たせ、追跡していない命令がその場所を書き換えたら (バイトが変わったら) 捨てる。
- 追跡する命令: MOVE (数値・英数字・グループ、JUSTIFIED RIGHT)、算術 (`Store` の加減乗、定数での除算、桁あふれの条件で
  SIZE ERROR)、一時変数、条件ジャンプ (比較・88 レベル・符号・クラス・NOT/AND/OR)、GO TO DEPENDING (値を
  固定する仮定)、ACCEPT (行のバイトが変数)、順次ファイルの READ、INSPECT (`vm/sym_text.rs`: BEFORE/AFTER のない
  1 句で、1 文字を対象とする TALLYING・REPLACING の ALL/LEADING/FIRST/CHARACTERS と CONVERTING。各バイトは
  `If(バイト = 対象, 置換, バイト)` の項、計数は `Σ If(…, 1, 0)`。1 文字の BEFORE / AFTER INITIAL は各位置が範囲の
  中かの条件と組み合わせる。64 バイトまで)、UNSTRING と STRING (区切りは複数文字も、または SIZE)、
  `FUNCTION LENGTH(FUNCTION TRIM(x))` (すべて空白なら 0、24 バイトまでは先頭と末尾の空白の数から正確に)、
  `TEST-NUMVAL(-C)` (数として正しければ 0)。
- UNSTRING / STRING: 受け取り側は、この実行での区切りの位置の間にある元のバイトの項。各受け取り側の先頭から
  32 バイトまでの「この位置は区切りか」を判定 (プログラム `P#TEXT`、網羅率には数えない) として記録するので、
  ソルバはそれを逆にして区切りを動かしたり足したりできる。部分参照の長さが入力に従う対象
  (`W01-GET-BUFFER(1:W01-DATALEN)`) は「長さ = 項目の長さ」も判定にする。NUMVAL・NUMVAL-C は「引数が数
  (空白・数字・小数点、数字を含む)」を判定にし (正しくない引数は実行を終わらせるため)、数のときは空白・数字・
  小数点の位置を固定した仮定のもとで数字から値の項を作る。
- 読み出し: 入力のバイトから、DISPLAY の数字 (この実行で数字のバイトは「数字のまま」という仮定付きで `バイト - X'F0'`、
  数字でないバイトはインタプリタと同じく下位の半バイト `バイト % 16`) に加えて 2 進 (COMP・COMP-5: ビッグ
  エンディアン、符号付きは 2 の補数) とパック 10 進 (半バイトごとの数字、最後の半バイトが符号) の数値を項として
  組み立てる。英数字の比較とクラス条件では、符号なし DISPLAY 整数を数値としてではなくバイトとして読む
  (`IF ACCTSIDI = '*'`、`IF WS-OPTION IS NOT NUMERIC`)。
- 記号の添字: 表の要素を、入力に従う添字 (1 つ。多次元の表ではほかの添字は具体値) で読むと「添字 = j なら j 番目の
  要素」の `If` の連鎖 (64 個まで) になり、添字が範囲内という仮定を付ける。定数の部分参照
  (`PGMNAME(WS-OPTION)(1:5)`) も扱う。書き込みの添字は具体値。
- 1 回の実行の変数は 20000 個まで (`concolic::MAX_VARS`)。超えたらスタブや EXEC の応答など外からのデータは追わない
  (状態コードが変わらないスタブでループするプログラムが、解けないほど大きな実行にならないように)。条件付きの
  判定は 50000 個まで (`MAX_STEPS`、超えたら条件なしで向きだけ記録)、データに結び付ける項は節点 2000 個まで
  (`MAX_TERM`、超えたら具体値)。変数は名前の索引で引く。判定が上限を超えた後は、その実行で初めての向きだけを
  記録し、仮定も記録しない (無限ループの実行で経路が数百万ステップにならないように)。
- 分岐は ZIR の `JumpIf`/`JumpUnless` 単位で記録する (複合条件は一つの判定なので C1 = 判定網羅で `zcov` と一致)。

### 入力

- LINKAGE: USING の各パラメーターの基本項目 (OCCURS は最大 100 個まで展開、重なりは先の項目を採用)。数値は値の
  変数一つ (`P1.LK-AMOUNT`)、英数字はバイトごとの変数 (`P1.LK-USER#3`)。名前が重なる項目 (FILLER など) は
  位置を付ける (`FILLER@12`)。
- ACCEPT: 実行した ACCEPT の n 番目の行のバイト (`ACCEPT1.4`)。
- 順次ファイル: プログラム (モジュールのもの、および `-L` の .zo から読み込める呼び出し先) が OPEN INPUT する ORGANIZATION SEQUENTIAL のファイルのレコードとその件数。
  READ で n 件目を読んだらレコード領域 (と INTO の先) の各項目が `F<ファイル>.R<n>.<項目>` に従い、件数
  `F<ファイル>.N` (0〜99) に対して AT END は `N <= n-1` の条件になる。FILE STATUS の 1 バイト目も件数の項
  (`'1'` か `'0'`) にするので、`IF WS-FS = '10'` の形の終了判定も解ける。
- 索引ファイル: 同じくプログラムが OPEN INPUT または I-O する ORGANIZATION INDEXED のファイル。レコード n の項目は
  読んだ順ではなく入力の n 件目の変数 (`F<ファイル>.R<n>.<項目>`)。条件は次のとおり。
  - キーによる READ (乱・動的アクセス): 「`N` 件のいずれかのキーが探索キーに等しい」が見つかる条件で、INVALID KEY
    はその否定。探索キー (レコード領域のキー) も入力に従う項になり得る。もう 1 件 (既定の内容の追加レコード) も
    候補に含めるので、ソルバは件数を増やしてキーを合わせれば「見つかる」向きを作れる。
  - START KEY >= / > / =: 同じ形で、キーの比較が関係に従う (探索キーがキーの先頭部分なら先頭部分で比べる)。
  - WRITE: 主キーが既存のどれかに等しいことが INVALID KEY (状態 22)。
  - READ NEXT: OPEN からの n 回目で AT END は `N <= n`。START の後は、残りの件数を「キーが関係を満たして存在する
    レコード」の数の項 (`Σ If(n < N ∧ キー rel 探索キー, 1, 0)`) とし、その後の n 回目で AT END は `残り <= n`。
    読んだレコードは主キーで入力のどれかを特定して従わせる。
  - 追加の 1 件には「主キーが既存のどのレコードとも違う」条件を付ける (同じキーにすると入力から除かれるため)。
  - FILE STATUS の 2 バイトは条件による項 (`Term::If`) で、"00" と "23" / "10" / "22" を表す。
  - WRITE・REWRITE・DELETE の後はデータセットが入力と違うので、それ以降のキーの条件と AT END は具体値。
    主キーや一意の副キーが重なるレコードは入力から除く (データセットに置けない)。
- 入出力エラー: FILE STATUS を持つファイルの OPEN・READ・WRITE・REWRITE・DELETE・START・CLOSE の、ファイルと
  種類ごとの n 回目を失敗させられる (変数 `F<ファイル>.<文><n>`、1 か 2 で失敗)。失敗した文は何もせず、状態は
  1 なら OPEN INPUT / I-O で 35、それ以外は 30、2 なら `'9'` と 2 進の X'10' (VSAM の論理エラーの形で、数字でない。
  ケースの `faults` に `"status": "F910"`)。FILE STATUS は `If(失敗, 状態, 本来の状態)` の項、入出力条件は
  「失敗 または 本来の条件」。ソルバはまず失敗させない (失敗の変数を 0 に固定した) 解を探し、なければ失敗を
  使う (通常の入力で通る経路は通常の入力で作る)。ケースの `faults` に記録し、`ztest` も同じ文を失敗させる。
- CALL のスタブ: 呼び出した名前のプログラムがモジュールにも `-L` にもないとき、試験の実行ではエラーにせず
  スタブにする。スタブは RETURN-CODE 0 で戻り、n 回目の呼び出しの BY REFERENCE の各引数 (先頭 256 バイト) は
  変数 `C<プログラム>.<n>.A<k>#<i>` に従う。ソルバが選んだ出力は `stubs` に記録し、再実行ではスタブがその
  バイトを引数に書く。`report.txt` と `expect.stubbed` にスタブにしたプログラムを示す。
- EXEC CICS・EXEC SQL: EXEC 文を含むプログラムは、トランザクションもデータベースも動かさないスタブ
  (`StubHost`) で実行する。プログラム `P` の行 `l` の EXEC 文の n 回目の実行が受け取る値がキー `P.l.n.<オプション>`
  の入力で、記号付きの実行では変数 `X<キー>` (数値) または `X<キー>#<i>` (バイト) に従う。ケースの `exec` に
  記録し、送った内容 (FROM、COMMAREA、RIDFLD、SQL 文と入力のホスト変数など) の列を期待値 `expect.exec` にする。
  - CICS: RESP・RESP2・INTO・LENGTH (READ・RECEIVE)・ASSIGN の各項目などが入力。INTO などがグループ項目なら
    基本項目ごとのキー (`P.l.n.INTO.ACCT-ID`) にし、数値の項目は値の変数にする。ただし RECEIVE (端末からの入力) の
    DISPLAY の数字項目はバイトの変数にする (`IF ACCTSIDI = '*'` のように英数字で調べるため)。RESP は EIBRESP にも
    入れる。RESP のないコマンドの応答は HANDLE CONDITION の飛び先 (IGNORE CONDITION・NOHANDLE なら無視、どちらも
    なければ実行の終わり) に従い、HANDLE された条件ごとに「応答 = その条件の値」の判定を記録する (プログラム
    `P#EXEC` の判定で、網羅率には数えない)。RETURN・XCTL はプログラムの終わり、ABEND はエラー。
  - SQL: SQLCODE (プログラムの SQLCA の項目の型で) と、INTO の後のホスト変数 (Db2 ホストと同じ規則: SELECT・VALUES・
    WITH の最上位の INTO から FROM まで、FETCH は全部、`SET :hv =` は先頭) が入力。SQLCODE が負・100・正なら
    WHENEVER SQLERROR・NOT FOUND・SQLWARNING の飛び先へ進む。
  - 既定: RESP と SQLCODE は 0。ただし FETCH と READNEXT・READPREV は 2 回目の実行から 100 と ENDFILE を返す
    (読み続けるループが終わる。ソルバは n 回目を 0 にして件数を増やせる)。
  - EIB を持つプログラムは EIBCALEN を COMMAREA の長さ (最大 1024) で始める (`MOVE DFHCOMMAREA(1:EIBCALEN)` の
    長さは記号として追わないため、短いと COMMAREA の内容が入力にならない)。要素が 1 バイトの OCCURS (COMMAREA の
    `OCCURS 1 TO 32767 DEPENDING ON EIBCALEN` など) は 100 個ではなく 1024 バイトまで項目に展開する。
- LE の日付・時刻のサービス (CEEDAYS・CEESECS・CEEDATE・CEEDATM・CEELOCT・CEEGMT): サービスは実際に動かし、
  その後で出力の引数 (結果とフィードバック・コード) を n 回目の呼び出しのスタブの出力 (`stubs` の
  `"program": "CEEDAYS"`) として入力にする。値がなければ実際の結果のまま。ソルバは実際には起こらない組合せも
  選び得る (特性テストとしての割り切り)。
- DL/I: EXEC DLI は INTO (項目ごと) と DIBSTAT が入力 (既定は空白、GN・GHN の 2 回目からは GB、GNP・GHNP は GE)。
  `CALL 'CBLTDLI'` (AIBTDLI・CEETDLI も) は DL/I 用のスタブで、PCB の状態コード (11〜12 バイト目) と get 呼び出しの
  入出力領域が、関数ごとの n 回目の出力 (`"program": "CBLTDLI.GN"`) になる。既定は同じく空白・GB・GE。
- 呼び出し先のスタブ (`--stub PROGRAM`): .zo があっても指定したプログラムはスタブにし、その出力を入力にする。
  再実行では、ケースがスタブにしたプログラム (`expect.stubbed`) をスタブにする。
- シード (`--seeds DIR`): ケースの JSON を初期入力として読む。前回の出力を与えれば生成結果の再利用になり、人が
  書く入力は `fields` に項目名と値だけを書けばよい (スタブの出力は `text` に文字で)。シードは最初に解かずに
  まとめて実行し、網羅を記録してから探索を始める。
- 時刻: 生成と再実行の時刻は 2025-01-01 09:00:00 UTC に固定する (`zeus_cobol::clock`)。CURRENT-DATE、
  ACCEPT FROM DATE/TIME、LE の日時、データセットの日付がこれを返すので、日時を書くプログラムでもケースが再現する。
  時刻を見るプログラム (CURRENT-DATE、ACCEPT FROM DATE など、ASKTIME) では時刻も入力で、年末の時刻からも始め、
  変異で日・月・年の境目とうるう日を試す。ケースの `clock` (`YYYY-MM-DD HH:MM:SS`、UTC) に記録する。
- すべてのファイルは実行ごとの一時ディレクトリーにデータセットを割り当てる。主プログラムが書いた順次ファイル、
  および OUTPUT・I-O・EXTEND で開いた索引ファイルの最終のレコードは期待値 (`expect.files`) に記録し、`ztest` で比べる。

### ソルバ

否定標準形にしたうえで、

1. 一変数の線形な原子式から変数の区間を求める (空なら充足不能の証明)。
2. 分岐距離を最小にする局所探索。候補は線形の根、二分、プログラムのリテラル、10 の冪、バイトや小さな範囲は全値。
   一手の評価はその変数を含む条件だけを計算し直す (差分)。予算は反復回数 (既定 400) と、向きの最初の試行で
   150 ms、2 回目以降と文脈を変えた解き直しで 50 ms。`--time` は解く途中でも確かめる。
3. 向きの最初の試行で局所探索が時間内に解けなければ Z3 (`smt.rs`)。条件を SMT-LIB (整数の算術、切り捨ての除算と
   剰余、バイト列の辞書順の比較) にして、実行時に読み込んだ `libz3` の `Z3_eval_smtlib2_string` に渡す (1 回 400 ms)。
   `libz3` は `ZTESTGEN_Z3`、システムの検索パス、Python のパッケージ `z3-solver` の順に探し、なければ局所探索だけで
   動く (`--no-smt` で使わない)。ビルドに Z3 は要らない。解なし (unsat) は到達不能の証明になる。

### 探索

- 世代探索: 実行の経路の各分岐について、未網羅の向きなら、それまでの条件のうち同じ変数につながるものだけを残して
  (スライス) 逆向きを解き、解を次の入力にする。向きごとの試行は 4 回まで。全試行が充足不能なら「到達不能」と報告。
  スライスは実行ごとに、条件の変数の素集合 (union-find、集合ごとにその条件) を経路の順に作って引く。
- 求解は実行ごとにまとめて、スレッド (`--threads`、既定はコア数で最大 8) ごとのソルバ (Z3 の文脈も別) で並列に解く。
- 静的な到達不能の証明 (`infeasible.rs`): 対象のプログラムの英数字のフラグ (定数だけを入れる WORKING-STORAGE の
  基本項目。CALL の引数、READ INTO、グループの MOVE、FILE STATUS などファイルの定義が指す項目、レコード領域と重なる
  ものは除く) の取り得る値を、制御の流れに沿って求める (VALUE と MOVE の定数、条件付きの飛越しの各向きで値を
  絞る。PERFORM の戻りは、その段落を PERFORM するどこへでも戻るとして過大に近似)。どの値でも通らない向きは
  「不可能」とし、試行をやめ、網羅率の分母から外す。網羅できた向きを不可能とした場合は誤りとして報告し、使わない。
- 有効化する判定: 同じ解析から、未網羅の向きが必要とするフラグの値を入れる MOVE の直前の条件付きの飛越しの向き
  (有効化する判定) を求める。その未網羅の向きまで届いた実行では、手前の有効化する判定を逆にする解き直しを
  (組ごとに 3 回まで) 行う。
- 実行の回数は既定で 2000 回まで (`--runs`)。命令数の上限は、正常に終わった実行の最大の命令数の 10 倍 (20 万以上、
  `--limit` 以下) にして、無限ループの実行を早く打ち切る。その上限で切れた実行はケースにしない (`ztest` の再実行は
  `--limit` までなので結果が変わる)。`ztest` の再実行にも `--limit` の上限をかける。
- HANDLE CONDITION と WHENEVER: 飛び先へ行く応答の判定 (プログラム `P#EXEC`) は網羅率には数えないが、最小化では
  網羅する向きとして扱うので、飛び先を通るケースが残る。
- 区切りの判定 (`P#TEXT`): 通算の網羅ではなく「同じ文のその位置より前の判定に現れる変数の値」(前のデータ) が新しい
  ときに逆向きを解く。解き直すのは、新しい向き (区切りの位置の判定を除く) を網羅した実行からだけで、生成全体で
  400 回まで。さらに、受け取り側の数より区切りが少なそうな実行は、最後の受け取り側の 8 バイト目に区切りを 1 つ
  足す (区切りの数ごとに 2 回まで)。これらの入力は通常のキューが空のときに実行する。
- 文脈を変えた解き直し: 網羅済みの向きでも、到達したのに条件が一度も入力に従わなかった向きが残る間は、
  その前に通った判定の組 (文脈) が新しければ逆向きを解く (向きごとに 12 文脈まで)。編集の段落で `SET … TO TRUE`
  したフラグ (88 レベル) による判定 (COACTUPC の画面のカーソル位置など) も、これで前の判定を変えて通す。CICS のプログラムでは、
  初回の経路 (画面の入力が定数) で網羅した判定を、RECEIVE した経路でも逆にしないと、その後の画面の項目による
  判定が入力に従わない。
- ループの深掘り: 条件が入力に陽に依存しない分岐 (ループで計算した値による判定など) が残るときは、最深の実行から
  ループの最後の判定を逆にして繰り返しを一回ずつ増やす (上限 20)。
- 変異: ソルバが尽きたら、境界値とプログラムのリテラルの辞書で入力の一項目 (ファイルは件数かレコードの項目) を変える。
- 最後に貪欲な集合被覆でケースを最小にする。

### 未実装と制限

- 段階 B の残り: 相対ファイル、LINE SEQUENTIAL の入力、多次元の表と書き込みの記号の添字、REDEFINES の
  バイト層での再解釈 (DISPLAY・2 進・パック 10 進の数値はバイトから読めるが、ゾーン 10 進の符号付き・浮動小数点は具体化)。索引ファイルのキーのうち符号付き・パック 10 進の項目はバイトの
  定数として扱う (そのキーの条件はそのレコードの値を変えられない)。
- 入出力エラーは 35・30 と `'9'` + X'10' だけ (VSAM の拡張状態は 0)。FILE STATUS のないファイルは失敗させない。
- 呼び出し先: `-L` の .zo のプログラムも記号付きで実行するが、網羅を数える分岐は対象のモジュールのものだけ。
  スタブの出力はバイト単位 (2 進・パック 10 進の項目として読むと数値の項になる)、RETURN-CODE は 0 のまま。
- 段階 C〜E の残り: 区切りなし (長さで分ける) の UNSTRING、複数句や複数文字の BEFORE/AFTER の INSPECT、
  段落の要約、C2・MC/DC、PL/I。
- 静的な証明は英数字のフラグだけ (数値の項目の範囲、表の件数による判定は扱わない)。入れ子のプログラムが GLOBAL の
  データを書くモジュールと再帰のプログラムでは行わない。
- EXEC CICS/SQL のスタブ: 下記「既知の課題」。
- 日付・時刻以外の LE の呼び出しや組み込み関数 (NUMVAL など) の結果は具体値で、それに依存する分岐は「入力に依存しない」と報告される。
- 非線形の算術 (変数どうしの除算、べき乗、浮動小数点) は具体化する。

## 向いているもの・向いていないもの (検証から)

自前の試験プログラム 9 本と CardDemo の 37 本 (バッチ 12、オンライン 17、IMS・Db2・MQ の拡張 8) で確かめた結果から、
この方式 (concolic 実行・自前の局所探索のソルバ・環境のスタブ) で網羅率を上げやすいものと難しいものをまとめる。
数値は `ztestgen` が報告し、`ztest` で全ケースの再現を確かめたもの。

### 網羅率を上げやすいもの

判定の条件が、入力 (またはスタブが返す応答) から**データの流れ**でたどれ、条件の形が比較・範囲・線形の算術に
収まるもの。実績は 90〜100%。

| 種類 | 例 (CardDemo) | C1 |
|---|---|---|
| 入力の値による判定: 比較、88 レベル、EVALUATE、符号・クラス条件、線形の算術と ON SIZE ERROR | CSUTLDTC、試験の SAMPLE | 100% (到達不能を除く) |
| 順次・索引ファイルを読む処理: AT END、INVALID KEY、FILE STATUS (35・30・`9x` の注入を含む)、件数とキーの関係 | CBACT01C〜03C、CBCUS01C、CBTRN01C〜03C、CBEXPORT、CBIMPORT | 96〜100% |
| 外部への要求の応答で分かれる処理: CICS の RESP・HANDLE CONDITION、SQLCODE・WHENEVER、DL/I の状態コード、CALL・LE サービスの結果 | COSGN00C、COBIL00C、COUSR00C〜03C、COTRN00C〜02C、CBPAUP0C、COPAUS0C〜2C、PAUDBUNL | 95〜100% |
| 画面の入力の検査: 英数字・数字の判定、IS NUMERIC、INSPECT (1 句)、右寄せ、1 次元の表の添字、定数の部分参照 | COMEN01C、COCRDLIC、COCRDSLC、COACTVWC | 88〜90% |
| 区切りのあるテキストを分けて使う処理 (UNSTRING・STRING・NUMVAL) | 試験の SPLITPGM、CORPT00C | 83〜100% |

共通するのは次の点。

- 入力が判定まで**値として**届く (MOVE、算術、比較、ファイルのレコード、応答の項目)。
- 外部の振る舞いが「応答の値」で表せる。スタブがその値を入力にするので、ソルバは NOTFND・SQLCODE 100・GB・
  状態 35 などを選べる。
- 判定どうしの組合せが少ない。向きごとに数回の解き直しで届く。

### 網羅率を上げにくいもの

残った向きを理由ごとに分けると次のようになる。上ほど多い。

| 理由 | 例 (CardDemo) | なぜ難しいか | できること |
|---|---|---|---|
| 起こり得ない判定 (ループの条件・表の件数・前の判定から決まる) | バッチの `IF END-OF-FILE = 'N'` の偽 (各 1〜2 向き)、COMEN01C・COADM01C の `WHEN 12` と 'DUMMY'、`EVALUATE` の `WHEN OTHER` | 本当に通らない。英数字のフラグによるもの (`IF END-OF-FILE = 'N'`) は静的な解析で「不可能」と証明し、分母から外す。数値の範囲や表の件数によるものはまだ「入力に依存しない」と報告される | 人が確認して除外する。静的な解析を数値の範囲・表の件数に広げる |
| 定数を代入したフラグを介した判定が多く、組合せが多い | COACTUPC (750 向き、71%)、COCRDUPC (86%)、COACTVWC | `SET … TO TRUE` したフラグは定数なので、判定そのものは入力に従わない。前の判定を逆にする「文脈を変えた解き直し」と「有効化する判定」(フラグに値を入れる MOVE の直前の判定) の解き直しで通すが、多くの項目が同時に正しい画面が要る判定 (COACTUPC のカーソル位置) には届きにくい | 正しい画面のシード (`--seeds`) を与える。`--runs`・`--time` を増やす |
| 環境や実行時の状態による判定 | CBSTM03A の TIOT (制御ブロック) の走査と ALTER (90%) | 入力ではなく z/OS の制御ブロックで決まる | 環境のモデルを足す (TIOT の DD の並び)。時刻は入力にした (CORPT00C の月の繰上げが通る) |
| 呼び出し先の内部の状態による判定 | CBSTM03A が CBSTM03B の戻りコードで分ける | `-L` の呼び出し先も記号付きで実行するが、網羅の目標は対象のモジュールの分岐だけ。戻りコードは呼び出し先のファイルの状態の組合せで決まる | `--stub` で呼び出し先をスタブにすれば戻りコードが入力になる (実装済み)。呼び出し先の分岐も目標にする (未実装) |
| 長い可変長のメッセージの組立て | COPAUA0C (MQ のメッセージを UNSTRING で 18 項目に分ける、72%) | 区切りの位置の判定が多く、解き直しの組合せが増える。60 秒の時間制限で止まる | 時間を増やす。メッセージの形 (項目の並び) を辞書として与える (未実装) |
| 追わない操作 | 変数どうしの除算・べき乗・浮動小数点、NUMVAL 以外の組込み関数 (TEST-NUMVAL-C、FUNCTION LENGTH など)、多次元の表や書き込みの添字、複数文字の区切り、BEFORE/AFTER の INSPECT、1024 バイトを超える領域 | 結果を具体値にするので、その後の判定は入力に従わない | 操作ごとに記号の層を足す (INSPECT・UNSTRING・2 進・パック 10 進はこの方法で足した) |
| ソルバが解けない条件 | 少数 (CardDemo では各数向き) | 局所探索なので、複数の変数の強い関係 (チェックディジット、ハッシュ)、長い等式の連鎖、狭い解は時間内に見つからず「入力が見つからない」になる | Z3 をつないだ (局所探索で解けないものを回す)。CBSTM03A・CBACT04C の残りが解けた |

### 網羅率とは別に注意すること

- **スタブの応答は現実にあり得るとは限らない。** ソルバは CICS・SQL・DL/I・MQ・LE の応答を自由に選ぶ。
  そのため「有効な日付なのに CEEDAYS がエラー」「READ が NORMAL なのにレコードが空」のようなケースもできる。
  網羅は上がるが、期待値 (現在の振る舞い) が業務上意味のある状況かどうかは人が確認する。
- **擬似会話の一貫性は保証しない。** COMMAREA と EIB は入力として作るので、前の画面から来たはずの状態
  (CDEMO-PGM-REENTER、前のマップ名など) を自由に組み合わせる。実際の画面遷移では起こらない状態のケースも混じる。
- **期待値は現在の振る舞い**で、仕様として正しいかは別に確かめる (特性テスト、回帰テストとして使う)。

### 使い方の目安

- バッチ (ファイルの入出力、サブプログラムの CALL) と、応答で分かれるオンラインは、既定の設定でほぼ 90% 以上になる。
  呼び出し先は `-L` で .zo を与えると実行され、なければスタブになる。
- 入力の検査が深いオンライン (更新画面など) は、`--runs` と `--time` を増やすと上がる。`report.txt` の
  「condition does not depend on the inputs followed」(入力に依存しない) が多いときは、フラグを介した判定か
  起こり得ない判定であることが多い。
- 残った向きのうち「not reached」(到達しない) は、その前の「入力に依存しない」向きを解決すると届くことが多い。

## 効率化と生成 AI のヒント (検討)

### 時間の使われ方

COACTUPC (750 向き) を 60 秒で生成したときの内訳は、求解がおよそ 85% (大半は時間切れで解けない求解) で、実行そのものは
1 割程度だった。網羅率は実行回数に比例して上がり (500 回で 66%、2000 回で 72%)、残りは定数のフラグを介した判定の
組合せだった。したがって効率は「解けない求解を減らす」「狙うべき判定を直接選ぶ」「実行を並べる」で上がる。

### 生成 AI を使わない効率化

| 手 | 効く対象 | 見込み |
|---|---|---|
| Z3 などの SMT ソルバを `Solver` トレイトでつなぐ (局所探索で解けないものだけを回す) | 局所探索が時間切れになる条件 (求解の時間の大半) | 解けるものが増え、解けない理由 (unsat) が証明になる。無駄な試行と、誤った「入力が見つからない」が減る |
| フラグの依存関係の静的解析 (どの判定のどちらの向きで、どのフラグにどの値が入るか) | `SET … TO TRUE` したフラグによる判定 (COACTUPC の残りの大半) | 「この判定はフラグ X で決まり、X はこの段落の判定で設定される」から、逆にすべき判定を直接選べる。今は文脈を手当たり次第に変えている |
| 到達不能の静的な証明 (ループの条件、表の件数、前の判定、定数の伝播) | バッチの残り 1〜2 向きのほぼすべて、`WHEN OTHER` | 網羅率は上がらないが、試行をやめられ、報告が「到達不能」と正しくなる (分母から外せる) |
| 実行と求解の並列化 | 全般 | 実行は互いに独立なので、コア数に応じて速くなる |
| シード (既存のテストデータ、本番データの写し、人が書いた入力) を初期入力にする | 形のある入力 (メッセージ、レコード) | 最初から妥当な形の入力で始められる |
| 生成結果の再利用 (プログラムの改修後に前回のケースを初期入力にする) | 回帰テストの作り直し | 改修で変わった部分だけを探索すればよい |

### 生成 AI のヒントは有効か

役割の分担を守れば有効と見込む。

- **生成 AI は入力の候補を出すだけ**にする。候補はエンジンがシードとして実行し、網羅したかどうかと期待値は実行の
  結果で決める。生成 AI が誤っても誤ったケースはできず、ケースは記録された入力で再現する。
- 生成 AI をソルバの代わりにはしない。EBCDIC・パック 10 進・バイトの位置の正確な計算は不得手で、局所探索や SMT の
  ほうが確実。

残る向きの種類ごとの見込み。

| 残る向き | 生成 AI のヒントの効果 | 理由 |
|---|---|---|
| 形のある長いメッセージの組立て (COPAUA0C の 18 項目の CSV、カード番号、日付) | 高い | 業務的に妥当な形のデータを作るのは得意。ソルバが区切りを 1 つずつ足すより早い |
| 定数のフラグの組合せ (COACTUPC の入力検査) | 中〜高 | コードを読んで「状態を 'X' にして与信限度を空欄にすると、このエラー表示を通る」のように画面の項目の組合せを提案できる。細部の値はエンジンが詰める |
| 環境・呼び出し先の状態 (CBSTM03A の TIOT、CBSTM03B の戻りコード) | 中 | スタブの応答の案は出せる。ただし本筋は環境のモデルを一度作ること |
| スタブの応答の妥当性 (あり得ない組合せのケース) | 中 (品質) | 「有効な日付なのに CEEDAYS がエラー」のようなケースの指摘や、妥当な組合せの提案ができる。網羅率より期待値の質に効く |
| 起こり得ない判定 | 低い (説明は役立つ) | 通す入力が存在しない。「ループの条件から到達しない」という説明は人の確認を助けるが、証明ではないので到達不能とは数えない |
| チェックディジットなどの厳密な制約 | 低〜中 | Luhn のような既知のアルゴリズムは提案できるが、純粋な制約は SMT ソルバのほうが確実 |

CardDemo で残った向きに当てはめると、生成 AI が直接効くのは COACTUPC のフラグの組合せの一部と COPAUA0C の
メッセージ。バッチの残り (起こり得ない判定) は静的な証明の担当になる。

### 組み込み方

1. `ztestgen --seeds DIR`: ケースの JSON と同じ形 (`params` の `fields` を項目名で、`files`、`exec`、`stubs`) の入力を
   初期入力として読む。項目名から値をバイトに直すのはエンジンが行う。生成 AI に限らず、人が書いた入力や既存の
   テストデータもそのまま使える。
2. `ztestgen` は通せなかった向きごとに、ヒントの材料を出す (`hints.json`): ソースの該当行と周辺、そこまでの条件を
   項目名で書いたもの、近くを通ったケースの入力 (項目名と値)、理由の分類 (入力に依存しない・到達しない・入力が
   見つからない)。
3. 外部の手順 (生成 AI を呼ぶスクリプト) が材料から入力の候補を作り、`--seeds` で再び `ztestgen` に与える。
   エンジンは候補を実行し、そこから concolic の探索を続ける。網羅した分だけがケースになる。
4. 呼び出しの回数に上限を設け、候補が新しい向きを網羅した割合を記録して効果を測る。

注意すること。

- ソースを外部のサービスに送ることになる。業務のプログラムなので、社内で動かすモデルを使うか、送る範囲 (該当の
  段落とデータ定義) を限るかを決める。
- 生成の過程は毎回同じにはならない。ただしケースは記録された入力で決まるので、`ztest` の再現性は変わらない。
- `ztestgen` 自体は生成 AI に依存させない (ヒントの材料を出し、シードを読むだけ)。生成 AI を使うかどうかは利用者の
  手順で選べるようにする。

## 改善の進め方

効果と費用、前提の関係から、次の順に進める。6 (生成 AI) を除き、1〜5・7・8 は実装した (状態の列)。各段階の終わりに CardDemo の 37 本で網羅率・所要時間・全ケースの
再現を測り、この文書の表を更新する。

| 順 | 内容 | 狙い | 測り方 |
|---|---|---|---|
| 1 | **シードの入口** (`--seeds DIR`、項目名指定の入力) と**生成結果の再利用** (前回のケースを初期入力にする) | 以降の手 (人・既存データ・生成 AI のヒント) の共通の入口。単独でも、妥当な形のデータから始められる | COPAUA0C に妥当なメッセージを 1 件与えたときの網羅率と時間 |
| 2 | **到達不能の静的な証明** (定数の伝播、ループの条件、表の件数、前の判定との矛盾) | 起こり得ない向きを分母から外し、試行をやめる。報告の「入力に依存しない」を減らす | 到達不能と分類された向きの数、バッチの「到達可能な向きに対する網羅率」 |
| 3 | **SMT ソルバの接続** (Z3。局所探索で解けないものだけを回す) | 解けない求解の時間を減らし、unsat を証明にする | 求解の時間の割合、「入力が見つからない」の数 |
| 4 | **フラグの依存解析と狙い撃ち** (フラグに値を入れる判定の向きを、フラグを読む未網羅の向きの手前で逆にする) | COACTUPC などの入力検査の深いオンライン | COACTUPC・COCRDUPC の網羅率と、同じ網羅率に要る実行回数 |
| 5 | **実行と求解の並列化** | 全般の所要時間 | 同じ網羅率までの時間 |
| 6 | **ヒントの材料の出力** (`hints.json`) と、生成 AI でシードを作る手順の試作 (社内で動かすモデルを想定) | 1〜5 で残る、意味のある組合せと形のあるデータ | 候補が新しい向きを網羅した割合、呼び出し 1 回あたりの網羅の増分 |
| 7 | **環境のモデルの拡充** (TIOT・制御ブロック、時刻を入力にする、呼び出し先をスタブにする選択肢) | CBSTM03A のような環境依存の判定 | CBSTM03A・CORPT00C の網羅率 |
| 8 | **記号の層の拡充** (多次元・書き込みの添字、複数文字の区切り、BEFORE/AFTER の INSPECT、組込み関数) と、段階 E (C2・MC/DC、PL/I) | 追わない操作で残る向き、適用範囲の拡大 | 該当の構文を使うプログラムの網羅率 |

実装の状態 (2026-10-19)。

- 1〜5: 実装した (上記「入力」「ソルバ」「探索」)。
- 7: 時刻を入力にすることと `--stub` は実装した。TIOT などの制御ブロックのモデルは未実装。
- 8: 1 つの記号の添字 (多次元の表も)、複数文字の区切り、1 文字の BEFORE/AFTER INITIAL の INSPECT、
  `LENGTH(TRIM(...))`・`TEST-NUMVAL` は実装した。書き込みの添字と段階 E は未実装。
- 6 (生成 AI) は未着手。

順序の理由。

- 1 は小さく、2・6・7 のどれにも要る入口なので最初に置く。
- 2・3 は残る向きの分類を正しくし、無駄な試行を減らす土台になる。これがないと、4 や 6 の効果を測るときに
  起こり得ない向きや解けない求解が混じる。
- 4 は残る向きが最も多い種類 (フラグの組合せ) を、生成 AI なしで狙う。6 で生成 AI に任せる範囲をここで絞る。
- 6 は 1〜5 で残ったものに限ることで、呼び出しの回数と外部に送る範囲を小さくする。
- 7・8 は効く範囲が個別のプログラムに限られるので後にする。

### 既知の課題

- **RECEIVE MAP**: INTO の記号マップ (`mapI`) の基本項目ごとに入力にするが、項目の長さ (`...L`) とデータの整合
  (入力した長さ・MDT) は取らない。HANDLE AID は扱わない (EIBAID は EIB の入力なので EVALUATE EIBAID は通る)。
- **SQL の判定**: CALL の OUT 引数、SELECT INTO のない複数行の結果、SQLSTATE・SQLERRD は入力にしない。
  FETCH の件数は実行ごとの SQLCODE の変数で表す (件数の変数ではない)。標識変数は常に 0 (NULL にしない)。
- **CICS の出力の判定**: 出力のオプションを名前の一覧 (`CICS_OUT`) で決めているため、コマンドによっては
  送る側の LENGTH・COMMAREA などを入力と誤る、またはその逆がある。RESP のないコマンドの応答は、HANDLE された
  条件の値だけを解く (ERROR の飛び先、HANDLE ABEND は試さない)。
- **UNSTRING の探索の費用**: 区切りの判定は受け取り側ごとに 32 位置まで、解き直しは 400 回までに抑えているが、
  長いメッセージを多くの項目に分けるプログラム (COPAUA0C) では実行回数がかさみ、時間制限で止まる。区切りの
  判定は前のデータごとに解き直すので、同じ形のメッセージの細かな違いで実行が増えることがある。
- **LE の出力**: 実際の結果ではなくソルバが選んだ値にもなるので、CEEDAYS が返さない組合せ (有効な日付で
  フィードバック・コードが誤り) のケースもできる。
- **網羅できない向きの扱い**: CardDemo で残る向きの多くはループの条件や表の件数から起こり得ない判定。
  区間で証明できず「入力に依存しない」と報告される (到達不能としては数えない)。
- **性能**: 記号の条件が大きくなる (索引ファイルの件数 × キーのバイト、FILE STATUS の `If` の入れ子) と解くのが
  遅くなる。1 回 300 ms の上限で打ち切るので、時間内に解けない向きは「入力が見つからない」と報告される。
- **ソルバ**: 自前の局所探索と Z3 (向きの最初の試行だけ)。Z3 を補助的な求解にも使うと時間が数倍になる
  (CBTRN02C で 11 秒が 64 秒) ので使っていない。
- **作業環境**: ビルド成果物でディスクがすぐ一杯になる。`target/debug/deps` の古い成果物と `target/debug/incremental`
  を消すと空く。
